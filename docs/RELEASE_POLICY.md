# Политика публичных релизов

Эта политика относится только к публичным артефактам ScumNeDjin. Она не
даёт разрешения на публикацию игровых файлов, чужих бинарников, конфигураций
серверов или пользовательских данных.

## Неподвижная история

- Стабильные релизы и их assets не удаляются и не заменяются «на месте».
- Исправление публикуется новым тегом и новым набором assets.
- Если старый релиз больше не рекомендуется, в новом release note указывается
  его преемник и причина; сам старый asset сохраняется для rollback.
- Prerelease помечается как prerelease и не должен подменять ссылку на
  стабильную версию.

## Типы артефактов

| Тип | Содержимое | Обязательные сведения |
| --- | --- | --- |
| Community source | Только публичные исходники и документация. | Commit/tag, SHA-256, граница поставки и команда проверки. |
| Host package | Версионированный установочный пакет для оператора. | Совместимость, backup/rollback, SHA-256 и проверенный путь установки. |
| Prerelease | Ранняя проверяемая сборка. | Явный риск, известные ограничения и отдельная метка prerelease. |

Имена файлов должны отличать source от host package и включать версию. Нельзя
выдавать один и тот же архив одновременно за универсальную developer- и
production-сборку.

## Перед публикацией

1. Выполните [BUILDING.md](../BUILDING.md) и относящиеся к изменению тесты.
2. Выполните `scripts/Test-PublicTree.ps1` и ручную проверку public boundary.
3. Проверьте, что в diff нет credentials, адресов окружений, player data,
   баз данных, дампов, игровых ассетов, UE4SS-бинарников или чужого кода без
   права на распространение.
4. Проверьте README, release notes, checksums и ссылки как пользователь,
   который не знает внутренней структуры проекта.
5. Для host package дополнительно подтвердите backup, rollback и совместимость
   на контролируемой среде. Успех HTTP health-check сам по себе не является
   доказательством игровой операции.

## Формат release notes

Каждый release note начинается с пяти коротких разделов:

1. **Назначение** — что именно выпущено.
2. **Совместимость** — проверенные версии и известные ограничения.
3. **Изменения для оператора** — что нужно сделать или не делать.
4. **Проверка** — команды, тесты и границы полученного доказательства.
5. **Rollback** — на какой сохранённый релиз можно вернуться.

Не публикуйте секреты, рабочие адреса, персональные платёжные реквизиты,
персональные данные или необработанные логи в release notes, issues и assets.

## Вклад в релиз

Изменения готовятся в fork/ветке, проходят DCO и review в pull request. Автор
релиза сохраняет [NOTICE](../NOTICE), [COPYRIGHT.md](../COPYRIGHT.md),
[AUTHORS.md](../AUTHORS.md) и правила
[TRADEMARK_POLICY.md](../TRADEMARK_POLICY.md). Добровольная поддержка не
меняет эти правила и не даёт отдельный канал публикации.
